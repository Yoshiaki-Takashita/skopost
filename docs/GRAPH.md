## 1. 危険経路の定義（SPEC §7 を仕様として書き直したもの）

### 1.1 用語

- **外部テキスト**：`untrusted_in_context` が真のとき、文脈には外から来た文（ページ・メール・道具の返り）が入りうる。
  この文は 1 つの「汚れうる場所」として丸める（DESIGN §2）。偽なら道は 0 本（例外的な設定。報告に明記）。
- **見る道具**：`mode == "allow"` の道具だけ。`ask` は「人が止める」。
- **実効の札**（SPEC §6）：置き場を畳み込んだ後の 6 項目 `reads_untrusted`・`args_leave`・`exec`・`net`・`secret`・`acts`。
  - exec ＝ `exec` または（`executes` な置き場に書ける）
  - net ＝ `net_out` または（`external` な置き場に書ける）
  - secret ＝ `reads_secret` または（`secret` な置き場を読める）

### 1.2 道（3 種類・2 段まで）

| 種類 | 形 | 条件 | 意味 |
|---|---|---|---|
| 実行 `exec` | `[T]` | T の実効 exec が真 | 外部テキスト → T が任意のコードを実行 |
| 操作 `act` | `[T]` | T の実効 acts が空でない | 外部テキスト → 送信・購入・削除・公開・権限付与・支払い |
| 持ち出し `exfil` | `[R, S]` | R の実効 secret が真、S の実効 net **または** args_leave が真（R＝S でもよい） | 外部テキスト → R が秘密を読む → S が外へ出す |

- 1 つの道具から exec と act の両方が出ることがある（別の道）。
- `via`：道を作った札の理由（exfil は (R の secret の理由, S の送る側の理由)。送る側は net を優先）。
- **確度**：道を作った札の確度の**弱い方**（不明 < 推 < 論 < 確）。declared 層は「宣言」（確度の外の印・v1 互換）。
- 順序：allow の道具の並びで、まず各道具の exec → act、次に読む側 × 送る側の二重の並び（v1 と同じ。報告のバイト一致）。

### 1.3 「不明は危険」の扱い（方針）

observed 層で書かれていない札・確度「不明」の札は能力が**ある**と仮定する（DESIGN §2・原則 5）。仮定した項目は
`EffectiveCaps.assumed` → 報告の「不明として危ない側に倒した項目」に出す。

| 札 | 不明のとき（方針 `v1`） | 不明のとき（方針 `monotone`） |
|---|---|---|
| 真偽 5 項目 | 真 | 真 |
| `acts` | 全 6 種 | 全 6 種 |
| `writes_stores` | **なし（[]）**・仮定として数えない | **全部の置き場**・仮定として数える |
| `reads_stores` | **なし（[]）**・仮定として数えない | **全部の置き場**・仮定として数える |

- 置き場由来の実効の札の確度：v1 は「論」。monotone で置き場の札が不明なら「不明」（仮定で導いたので）。
  `via` には `writes_stores(不明→全置き場)→ext（外部の置き場）` のように仮定を書く。
- **既定は `v1`**（契約・報告のバイト一致のため）。`monotone` は `graph.harm_paths_policy(cfg, layer, "monotone")`・
  `graph.analyze_policy(cfg, "monotone")`・差は `graph.policy_diff(cfg)`。

### 1.4 段 1 の食い違いと直す案

段 1 の記録（ARCHITECTURE「段 1 で見つけたこと」1）：v1 は置き場の札が不明なら「置き場なし」と読むので、
**置き場の札を不明にすると道が減る**ことがある（例：`w` が外部の置き場に書ける＝持ち出しの送る側。`writes_stores` を
不明にすると送る側でなくなり、道 `r>w` が消える）。これは約束「不明を足しても道は減らない」（ARCHITECTURE §1.3 F1）
に反する。v1 の注記は「置き場の性質で倒す方が過大警報にならない」。

直す案＝方針 `monotone`：**置き場の札が不明なら全部の置き場に書ける／読めると倒す**。これで F1 は**全項目**で成り立つ
（試験 `test_graph_paths.MonotonePolicy.test_monotone_all_caps`・`test_monotone_random_many`・
`test_graph_props.Monotone.test_paths_never_shrink`：乱数 300 構成 × 全 8 項目で破れ 0・確）。
v1 で F1 が破れるのは置き場の札だけであることも試験で確かめた（`test_v1_breaks_only_on_store_caps`・確）。

代償（確・乱数 1,000 構成・`helpers.gen_raw_config` の分布で）：

| 指標 | 値 |
|---|---|
| monotone で道が増える構成 | 245 / 1,000 |
| 増えた道の本数 | 1,145（v1 13,378 本 → monotone 14,523 本・+8.6%） |
| 関所の最小数が増える構成 | 64 / 1,000 |
| monotone で道が**減る**構成 | 0（monotone は v1 の上位集合・試験 `test_monotone_is_superset_of_v1`） |

これは「誤報」でなく「置き場の札を書いていない代償」（LIMITATIONS）。観察の札に `writes_stores`・`reads_stores` を
書けば v1 と同じ数に戻る。

**決めてほしい点**：既定を `monotone` に切り替えるか。切り替えると (a) SPEC §6 に「置き場の札が不明なら全置き場」を
足す、(b) 契約試験 `HarmPathsMatchV1`・`AnalyzeMatchesV1` と黄金ファイルの更新（担当 A）、(c) 報告の「仮定した項目」に
`writes_stores`／`reads_stores` が増える、が要る。旧 compat/v1.py は変えない（凍結）。graph の側は 1 行
（`caps.DEFAULT_POLICY`）で切り替えられる。

## 2. 最小関所（最小ヒッティングセット）の厳密解

### 2.1 問題

allow の道具を頂点、道の道具集合（大きさ 1 か 2）を「当てるべき集合」として、すべてに当たる頂点集合のうち
**(個数, frequency の合計) を辞書式に最小**にするもの。同点は v1 と同じ鍵（道具 id を allow の並び順に並べた列の
辞書順＝文字列比較）。これは**最小ヒッティングセット**で、集合の大きさが 2 以下なので「強制頂点＋最小頂点被覆」。

### 2.2 手順（`hitting.solve`）

1. **強制**：単独の道 `[T]`（R＝S の持ち出しも含む）の T は必ず関所。これで断てる道を外す。残りは 2 個組だけ＝辺。
2. 辺が無ければ自明（`method="trivial"`）。
3. 残りの辺が**二部**なら重み付き最小頂点被覆を最大流で解く（König–Egerváry。`method="bipartite-konig"`。Dinic）。
   重み w(v) = BIG + frequency(v)、BIG = Σ frequency + 1。これで重みの最小＝(個数, 手間) の辞書式最小。
4. 二部でなければ**分枝限定**（`method="branch-and-bound"`）。下界＝極大マッチング（辺ごとに軽い方の重み）、
   次数 0 の除去、次数 1 の規則（相手の方が軽ければ相手を取る）、分枝は次数最大の頂点（入れる／入れずに隣を全部入れる）。
5. **同点の処理**：同じ個数の被覆を列挙し、(手間, 鍵) で並べて第一案と代替案（最大 5 件）にする。列挙は手間の上位
   `max_alternatives + 1` 件より重い枝を切る（同じ手間は切らない）ので、最小の (手間, 鍵) は決して落ちない。
   列挙を打ち切ったとき（節 200,000・被覆 20,000・時間）は、第一案を**制約付きの再解**で位置ごとに決める
   （「この道具を次に入れ、それより前の道具は入れない」という制約で最適値が変わらない最小の id を選ぶ）。
   これにより**同じ大きさの案が 200 件を超えても最小手間を逃さない**（v1 は 200 件で打ち切る。段 1 の記録 3）。
6. 道具が `exact_limit` を超え、かつ時間切れ（`time_budget_s`）／予算 0 なら、v1 と同じ**貪欲法**＋下界を返す。
   `exact` は「貪欲の大きさ＝下界」のときだけ真（個数の最小は証明できる）。**このとき手間の最小性は保証しない**。

### 2.3 構造の発見（確）

SPEC §7 の道を**全部**渡したときは、R と S の両方に入る道具が強制され（`[t,t]` は単独の道）、残りの辺は
「読むだけの R'」と「送るだけの S'」の間の**完全二部グラフ**になる。完全二部の最小頂点被覆は小さい側の全部（同数なら
手間の小さい側）なので、答えは本質的に O(道具数) で、代替案は最大 1 件。すなわち**v1 の 200 件打ち切りが効く構成は、
道の全部を渡す限り存在しない**。打ち切りが効くのは、道の部分集合（確度で絞る・将来の 3 段）を渡したときだけ。
試験 `TiesBeyondV1Cap` は 9 本の互いに素な辺（512 案）で v1 が最小手間を逃し、新実装が逃さないことを確かめる。

### 2.4 実測（確・Python 3.11・この環境・`SKOPOST_GRAPH_BENCH=1 python3 -m unittest tests.test_graph_bench`）

| 形 | 件数 | 平均 | p95 | 最大 | 厳密 |
|---|---|---|---|---|---|
| SPEC の道の全部・64 道具（観察の札の半分が不明・道 2,700 本前後）`analyze` 全体 | 50 | 0.032 s | 0.051 s | 0.063 s | 50/50（trivial） |
| 任意の二部の辺 32×32・辺 500 本（最大流） | 50 | 0.003 s | 0.005 s | 0.008 s | 50/50 |
| 任意の辺 64 頂点・辺 500 本（非二部・分枝限定） | 50 | 0.13 s | 0.21 s | 0.26 s | 50/50 |
| 任意の辺 64 頂点・辺 100 本（疎・分枝限定） | 50 | 0.027 s | 0.070 s | 0.083 s | 50/50 |

辺の本数を 100〜1,500 で振った追加の計測（各 50 件）：p95 は 0.04〜0.20 s、最大 0.25 s、時間切れ 0。frequency が全部
同じ（同点だらけ）の 64 頂点・辺 300 本でも最大 0.26 s・列挙の打ち切り 0。

- G2（n=64・道 500 本で p95 < 2 s）は**成立**（確）。ただし計測はこの環境・この乱数の分布で、最悪の構成（分枝限定が
  指数的に膨らむ特殊なグラフ）は探していない（**不明**）。時間切れのときは貪欲に落ちて `exact=False` と下界を返すので、
  嘘にはならない（試験 `GreedyFallback.test_timeout_returns_honest_answer`）。
- `MAX_TOOLS` を 64 → 256 に上げる判断（ARCHITECTURE §2.2）：SPEC の道の全部なら構造上 O(n) なので問題ない（論）。
  任意の辺の分枝限定は 256 頂点では**測っていない**（不明）。ビット集合は Python の int なので 64 を超えても動く。

### 2.5 試験（`tests/test_graph_hitting.py`・`test_graph_props.py`）

- 総当たりとの一致（G1）：道具 ≤ 10 の乱数 400 件＋同点だらけ 200 件＋id が辞書順と並び順で食い違う 200 件＋
  非二部の密なグラフ 100 件で、個数・手間・鍵（同点の順）・代替案の上位まで一致（確）。3 つの経路
  （trivial／bipartite-konig／branch-and-bound）を全部通ることも確かめる。
- König と分枝限定の一致（G3）：二部の乱数 200 件で重みが一致（確）。
- 近似のとき `lower_bound ≤ 真の最小 ≤ |primary|`（G4）：乱数 200 件（確）。貪欲は v1 と同じ案（60 件・確）。
- 性質：単調性（上）・最小性（どの関所を外しても道が残る）・冪等（第一案を当てたら道 0・もう一度当てても同じ・
  解析は決定的）・順序不変（道具と置き場の並びを入れ替えても道の集合・関所の個数と手間・案の集合は同じ）。

## 3. 既存の挙動との差（まとめ）

| 項目 | v1（compat・凍結） | graph（既定） | graph（monotone） |
|---|---|---|---|
| 道の定義・順序・確度 | SPEC §7 | 同じ | 置き場の札が不明なら全置き場（道は増えるだけ） |
| 第一案（≤ 20 道具） | 全探索・同じ大きさ 200 件で打ち切り | 厳密・**打ち切りなし**（最小手間を逃さない） | 同じ |
| 第一案（> 20 道具） | 貪欲・`exact=False` | 予算内（既定 5 秒）で厳密を試み、時間切れなら貪欲＋下界 | 同じ |
| 代替案 | 同じ大きさ・手間順・最大 5 | 同じ（列挙を打ち切ったときは一部。`analyze` の not_checked に明記） | 同じ |
| `Checkpoints.method`／`lower_bound` | exhaustive／greedy・下界なし | trivial／bipartite-konig／branch-and-bound／greedy・下界あり | 同じ |
| 仮定した項目 | 真偽 5 項目と acts | 同じ | ＋ writes_stores／reads_stores |

v1 との差が出るのは「道の部分集合を渡して同点が 200 件を超える」ときだけで、SPEC の道の全部を渡す解析では
結果は v1 と同値（契約試験 `AnalyzeMatchesV1`・秒数と代替案の中身を除く・確）。cli の配線はまだ compat.v1 のまま
（切り替えは担当 A・統合の順番は未定）。

## 4. graph が自前で持つ計算（infer との重なり）

`caps.effective`・`analysis.mismatches`・`analysis.assumed_unknown` は infer（担当 C）と意味が重なる。graph が持つ理由：
(1) 「不明」の倒し方の切り替えは危険経路の定義そのもの（graph の根幹）、(2) 段 2 は並行実装で infer を待てなかった。
infer が入った時点で `tests/test_graph_paths.CrossCheckWithInfer` が全構成で一致を確かめる（この文書の時点で infer は
入っており、一致・確）。将来どちらかに寄せるなら、方針の引数を infer.effective に足すのが筋（担当 A の判断）。
